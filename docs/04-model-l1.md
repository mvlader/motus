# MOTUS — модель для L-1

Оценщик сигнала (L-1, `appraisal.py`) переводит текст в шесть маленьких чисел по
жёсткой JSON-схеме (`Appraisal.json_schema()`). Это не диалог и не рассуждение —
классификация одного короткого сообщения по шести признакам. Модель для этой работы
должна быть маленькой и быстрой в первую очередь, а не умной: рассуждать тут не над
чем, и переплата токенами/задержкой в фоновом сенсоре, который дёргается на каждое
сообщение, накапливается быстрее всего в системе.

## Выбор: Qwen3 0.6B

```bash
ollama pull qwen3:0.6b-q4_K_M
```

- **Уже тот же вендор и тот же тулинг**, что и `qwen3:1.7b-q4_K_M` /
  `qwen2.5:3b-instruct-q4_K_M`, прописанные в openclaw как `utilityModel` — тот же
  формат промптов, тот же квантователь, тот же способ обновления.
- **Многоязычность** — 119 языков в семье Qwen3, включая русский. Сообщения
  пользователя приходят по-русски, а зарубежные компактные модели (Gemma, Phi) на
  младших размерах на русском заметно слабее в zero-shot.
- **Apache 2.0**, вес ~370 МБ в q4_K_M (523 МБ в q8_0), контекст 40K — с запасом для
  промпта из шести признаков.
- **Умеет выключать рассуждение** (thinking-mode toggle) — для L-1 это нужно
  выключить: рассуждение тут не помогает точности, а только тратит токены и время.
- Поддерживает structured output ollama (`format` = JSON-схема, с 0.3.0+) —
  используется в `ollama_sensor()`.

## Что уже подключено

`motus/appraisal.py:ollama_sensor(cfg)` собирает `sensor`-callable поверх
`urllib` (без внешних зависимостей — тот же принцип, что и у всего проекта) и
передаёт `Appraisal.json_schema()` в поле `format` запроса к `/api/generate`.
Схема ограничивает декодирование самим набором допустимых значений (grammar-
constrained decoding), а не только синтаксисом JSON — это первый рубеж защиты,
**до** `Appraisal.parse()` внутри `Appraiser.appraise_text()`. Рубежа два, не
один: сенсор может быть подменён на модель без поддержки схемы, и тогда работает
только `parse()`.

Событие `user_message` теперь можно слать с сырым текстом вместо готовой оценки:

```bash
curl -s -XPOST localhost:18790/event \
  -d '{"kind":"user_message","payload":{"text":"наконец-то заработало, спасибо!"}}'
```

`Engine.submit_event` сам вызывает сенсор, получает шесть чисел и **сразу
выбрасывает исходный текст** — в журнал уходит только производный результат, не
содержание сообщения. Тот же принцип, что и «карточка не пишется в память как
текст» (README, «Два правила»). Побочный эффект: реплей остаётся полностью
офлайновым и детерминированным — он читает уже посчитанный `appraisal` из журнала
и никогда не обращается к сети повторно.

Если `appraisal.enabled: false` (по умолчанию) или сенсор не смог ответить —
`Appraiser.appraise_text()` ловит любое исключение и возвращает нули; событие всё
равно проходит (контакт сбрасывает PANIC безусловно, см. `impulses()`), просто
без оценки содержания. Система не имеет единой точки отказа от одной упавшей
локальной модели.

## Включение

```json
"appraisal": {
  "enabled": true,
  "base_url": "http://host.docker.internal:11435",
  "model": "qwen3:0.6b-q4_K_M",
  "timeout_s": 3.0,
  "num_predict": 80,
  "temperature": 0.0
}
```

`config/default.json`, секция `appraisal`. Выключено по умолчанию **намеренно** —
включать после того, как модель скачана и вручную проверена на нескольких
сообщениях (см. ниже), а не сразу при первом деплое демона.

Проверка вручную, без демона:

```bash
python3 -c "
from motus.appraisal import ollama_sensor
s = ollama_sensor({'base_url':'http://localhost:11434','model':'qwen3:0.6b-q4_K_M'})
print(s('наконец-то заработало, спасибо большое!'))
"
```

Ожидается что-то вроде `{'valence': 2, 'threat': 0, 'novelty': 0, 'social_warmth': 2,
'loss': 0, 'agency_blocked': False}`.

`temperature: 0` — намеренно: это классификация с фиксированной схемой, а не
творческая генерация, разброс тут не нужен и только мешает воспроизводимости при
отладке через реплей.

## Путь апгрейда: Gemma 3 270M

Если после недели работы захочется срезать задержку ещё сильнее — Google
[Gemma 3 270M](https://developers.googleblog.com/en/introducing-gemma-3-270m/),
270M параметров, ~170–290 МБ в int4. Явно спроектирована под классификацию,
извлечение сущностей и структурирование текста — практически дословно наша задача
L-1. Не взята сразу по одной причине: Google сам позиционирует её как «требует
дообучения под конкретную задачу» — она меньше и быстрее, но без тонкой настройки
на русском может отвечать менее стабильно в zero-shot, чем Qwen3 0.6B.

Естественный путь: пока накапливается журнал (в нём уже есть
`appraisal_invalid` — сколько раз сенсор отказал или дал невалидный ответ), потом
на собранных примерах сделать короткий LoRA-файнтюн Gemma 3 270M под нашу схему —
дообученная 270M-модель на классификации обычно обгоняет недообученную 0.6B.
Апгрейд, а не замена на старте.

## Почему не более крупные модели

`qwen2.5:3b-instruct` (уже настроен как `utilityModel`) и тем более
`gpt-oss-20b`/`claude-sonnet-5` — для L-1 избыточны: она дёргается на каждое
сообщение пользователя, то есть чаще любого другого вызова модели в системе.
Разница в 5–10× по размеру здесь — это разница в задержке и нагрузке на Pi, а не
в точности: задача не требует рассуждения, только считывание шести очевидных
признаков короткого текста.
