# MOTUS — модель для L-1

## Где это работает физически (важно перед выбором)

`motusd` — обычный systemd-процесс на самой машине (`deploy/motusd.service`), **не
контейнер**. Ollama на этой же машине тоже не в контейнере — контейнер тут только
у openclaw (`~/.openclaw`, Docker). Поэтому схема простая:

```
┌─────────────────────── Raspberry Pi (хост) ───────────────────────┐
│                                                                    │
│   ollama (слушает :11435)  ◄──── motusd (127.0.0.1:11435) ────┐   │
│         ▲                                                     │   │
│         │ host.docker.internal:11435                         │   │
│  ┌──────┴───────────────┐                                    │   │
│  │  openclaw (в Docker)  │──── host.docker.internal:18790 ────┘   │
│  └────────────────────────┘         (motusd отдаёт карточку)     │
└─────────────────────────────────────────────────────────────────┘
```

**Ставить модель в контейнер openclaw не нужно.** `ollama pull` выполняется один
раз на хосте, там же, где уже стоят `qwen3:1.7b` и `qwen2.5:3b` — и `motusd`, и
openclaw обращаются к одному и тому же ollama, просто с разных сторон границы
контейнера, поэтому и адреса разные: `motusd` (сам не в контейнере) идёт напрямую
на `127.0.0.1:11435`, а openclaw (в контейнере) — через докеровский алиас
`host.docker.internal:11435`. Раньше в конфиге стоял второй адрес и для `motusd`
тоже — это было ошибкой (`host.docker.internal` резолвится только внутри Docker),
уже исправлено.

## Прогони сам — я не дотягиваюсь до твоего Pi

У меня нет сетевого пути до твоей машины (проверял: `host.docker.internal` и
`127.0.0.1:11434` из этой среды не отвечают — я в другом контейнере). Поэтому
цифры «Qwen3-0.6B быстрее» дальше в этом файле — из чужих опубликованных
бенчмарков, не с твоего железа. Замерь сам, это две команды:

```bash
ollama pull qwen3:0.6b-q4_K_M
ollama pull gemma3:270m
python3 tools/bench_l1_model.py
```

Скрипт (`tools/bench_l1_model.py`) гоняет обе модели через тот же промпт и ту же
JSON-схему, которыми `motusd` будет пользоваться в бою, на восьми разных
русскоязычных сообщениях. Меряет не секундомером снаружи, а честными цифрами
из самой ollama (`eval_count`/`eval_duration`) — задержка сети и время загрузки
модели в счёт не идут. И — важно — не только скорость: печатает валидный ли
JSON вернула модель и что конкретно она ответила на каждое сообщение, чтобы
видно было вживую, не отвечает ли быстрая модель просто мусором. Есть
`--out result.json`, если захочешь сохранить сырые цифры и прислать их сюда —
разберу вместе.

## Что вообще оценивает L-1

Оценщик сигнала (L-1, `appraisal.py`) переводит текст в шесть маленьких чисел по
жёсткой JSON-схеме (`Appraisal.json_schema()`). Это не диалог и не рассуждение —
классификация одного короткого сообщения по шести признакам. Модель для этой работы
должна быть маленькой и быстрой в первую очередь, а не умной: рассуждать тут не над
чем, и переплата токенами/задержкой в фоновом сенсоре, который дёргается на каждое
сообщение, накапливается быстрее всего в системе.

## Почему не Gemma 4 (и не по ссылке `gemma-4-E2B-it-assistant`)

Две отдельные причины, обе выясняются до всякого бенчмарка — по карточкам моделей:

1. **Ссылка не на самостоятельную модель.** `google/gemma-4-E2B-it-assistant` —
   78M-параметровый черновик для спекулятивного декодирования (Multi-Token
   Prediction). Он не работает один: обязан грузиться вместе с полной
   `google/gemma-4-E2B-it` и только предлагает токены-кандидаты, которые та
   потом проверяет. По этой ссылке в память попадёт не «маленькая модель», а
   вторая модель поверх основной.
2. **Сама Gemma 4 E2B — не маленькая.** «2.3B эффективных параметров (5.1B со
   всеми весами)» — это экономия вычислений у Gemma по сравнению с *плотной*
   моделью того же размера (часть эмбеддингов не участвует в горячем пути), а
   не превращение 2.3B в 0.6B. На CPU считается forward pass по активным весам,
   а не то, сколько их лежит на диске — и там всё равно в 4–8 раз больше
   вычислений, чем у Qwen3-0.6B. Плюс E2B мультимодальна (текст+картинка+звук):
   энкодеры изображения и звука занимают место и в памяти, и в весе модели, а
   L-1 они не нужны вообще.

Так что если сравнивать честно — не «Gemma лёгкая, Qwen тяжёлая», а наоборот:
из всего, что обсуждалось, Gemma 4 E2B — самый тяжёлый вариант, а не самый
лёгкий. Дальше — два реальных маленьких кандидата, и почему инстинкт «не грузить
на слабый ARM CPU что-то лишнее» правильный сам по себе, просто был направлен не
туда.

## Кандидат A: Qwen3 0.6B

```bash
ollama pull qwen3:0.6b-q4_K_M
```

- **Уже тот же вендор и тот же тулинг**, что и `qwen3:1.7b-q4_K_M` /
  `qwen2.5:3b-instruct-q4_K_M`, прописанные в openclaw как `utilityModel` — тот же
  формат промптов, тот же квантователь, тот же способ обновления.
- **Многоязычность** — 119 языков в семье Qwen3, включая русский.
- **Apache 2.0**, вес ~370 МБ в q4_K_M (523 МБ в q8_0), контекст 40K — с запасом для
  промпта из шести признаков.
- **Умеет выключать рассуждение** (thinking-mode toggle) — для L-1 это нужно
  выключить явно: рассуждение тут не помогает точности, а только тратит токены и
  время. Если раньше казалось, что Qwen3 «медленный» — вероятная причина либо это
  (включённый по умолчанию thinking), либо путаница с `qwen3:1.7b` (который стоит
  сейчас как `utilityModel` — втрое крупнее) или с Qwen3-MoE-вариантами
  (`Qwen3-Next`/`Qwen3-Coder-Next`), у которых в llama.cpp документированы баги
  именно на CPU/ARM — но это болезнь MoE-роутинга в другой архитектуре, к
  плотной 0.6B отношения не имеющая.
- Поддерживает structured output ollama (`format` = JSON-схема, с 0.3.0+) —
  используется в `ollama_sensor()`.

## Кандидат B: Gemma 3 270M

```bash
ollama pull gemma3:270m
```

- **Меньше и быстрее**: 270M параметров, ~170–290 МБ в int4 — в 2–3 раза меньше
  Qwen3-0.6B.
- **Спроектирована именно под эту задачу**: Google прямо называет классификацию,
  извлечение сущностей и структурирование текста целевыми применениями — это
  почти дословно работа L-1.
- **Риск** — Google сам позиционирует её как модель, которая «раскрывается после
  дообучения под конкретную задачу»; без тюнинга в zero-shot на русском может
  отвечать менее стабильно. Это не значит «не подходит» — значит «надо
  проверить `valid_json_rate` и качество ответов бенчмарком», не считать
  на глаз. Если `bench_l1_model.py` покажет высокий процент валидного JSON и
  разумные значения на русских примерах — она вполне может выиграть просто по
  паре чисел размера.

Естественный путь апгрейда, если сходу не дотягивает: в журнале уже пишется
`appraisal_invalid` (сколько раз сенсор отказал или дал невалидный ответ) —
на собранных примерах можно сделать короткий LoRA-файнтюн под нашу схему.
Дообученная 270M-модель на узкой классификации обычно обгоняет недообученную
0.6B — но это отдельная работа, не то, с чего стоит начинать.

## Что уже подключено

`motus/appraisal.py:ollama_sensor(cfg)` собирает `sensor`-callable поверх
`urllib` (без внешних зависимостей — тот же принцип, что и у всего проекта) и
передаёт `Appraisal.json_schema()` в поле `format` запроса к `/api/generate`.
Схема ограничивает декодирование самим набором допустимых значений (grammar-
constrained decoding), а не только синтаксисом JSON — это первый рубеж защиты,
**до** `Appraisal.parse()` внутри `Appraiser.appraise_text()`. Рубежа два, не
один: сенсор может быть подменён на модель без поддержки схемы, и тогда работает
только `parse()`.

Событие `user_message` теперь можно слать с сырым текстом вместо готовой оценки:

```bash
curl -s -XPOST localhost:18790/event \
  -d '{"kind":"user_message","payload":{"text":"наконец-то заработало, спасибо!"}}'
```

`Engine.submit_event` сам вызывает сенсор, получает шесть чисел и **сразу
выбрасывает исходный текст** — в журнал уходит только производный результат, не
содержание сообщения. Тот же принцип, что и «карточка не пишется в память как
текст» (README, «Два правила»). Побочный эффект: реплей остаётся полностью
офлайновым и детерминированным — он читает уже посчитанный `appraisal` из журнала
и никогда не обращается к сети повторно.

Если `appraisal.enabled: false` (по умолчанию) или сенсор не смог ответить —
`Appraiser.appraise_text()` ловит любое исключение и возвращает нули; событие всё
равно проходит (контакт сбрасывает PANIC безусловно, см. `impulses()`), просто
без оценки содержания. Система не имеет единой точки отказа от одной упавшей
локальной модели.

## Включение

```json
"appraisal": {
  "enabled": true,
  "base_url": "http://127.0.0.1:11435",
  "model": "qwen3:0.6b-q4_K_M",
  "timeout_s": 3.0,
  "num_predict": 80,
  "temperature": 0.0
}
```

`config/default.json`, секция `appraisal`. `base_url` — `127.0.0.1`, не
`host.docker.internal`: `motusd` не в контейнере, см. схему в начале файла.
`model` — то, что выиграло у `tools/bench_l1_model.py`. Выключено по умолчанию
**намеренно** — включать после бенчмарка и ручной проверки на нескольких
сообщениях (см. ниже), а не сразу при первом деплое демона.

Проверка вручную, без демона:

```bash
python3 -c "
from motus.appraisal import ollama_sensor
s = ollama_sensor({'base_url':'http://127.0.0.1:11435','model':'qwen3:0.6b-q4_K_M'})
print(s('наконец-то заработало, спасибо большое!'))
"
```

Ожидается что-то вроде `{'valence': 2, 'threat': 0, 'novelty': 0, 'social_warmth': 2,
'loss': 0, 'agency_blocked': False}`.

`temperature: 0` — намеренно: это классификация с фиксированной схемой, а не
творческая генерация, разброс тут не нужен и только мешает воспроизводимости при
отладке через реплей.

## Почему не более крупные модели

`qwen2.5:3b-instruct` (уже настроен как `utilityModel`) и тем более
`gpt-oss-20b`/`claude-sonnet-5` — для L-1 избыточны: она дёргается на каждое
сообщение пользователя, то есть чаще любого другого вызова модели в системе.
Разница в 5–10× по размеру здесь — это разница в задержке и нагрузке на Pi, а не
в точности: задача не требует рассуждения, только считывание шести очевидных
признаков короткого текста.
